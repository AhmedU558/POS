REST API SPECIFICATION
Integrated POS, Inventory & Business Management System
Java 21 • Spring Boot 3.x • REST • Version 1.0


1. Purpose & Scope
This document defines the HTTP API contract for the POS Management System. It specifies endpoint conventions, authentication, authorization, request and response structures, validation, error handling, pagination, idempotency, and module-level endpoints.
The API is intended to serve POS terminals, administrative web interfaces, online-order integrations, reporting interfaces, and future mobile clients.

4.3 Authorization
Every protected endpoint must enforce authorization server-side. Permissions should use stable codes such as PRODUCT_READ, PRODUCT_WRITE, SALE_CREATE, SALE_REFUND, INVENTORY_ADJUST, REGISTER_CLOSE, AP_PAYMENT_CREATE, and REPORT_VIEW.

5.4 Filtering
Resources should expose documented query parameters for status, store, category, date range, customer, supplier, and other relevant business filters. Unknown filters should be rejected rather than silently ignored when practical.
6. Idempotency
Financial and integration endpoints that may be retried must support idempotency. Clients may provide:
Idempotency-Key: <unique-client-generated-key>
POST /sales for externally retried checkout operations.
POST /payments where payment provider retry behavior exists.
POST /online-orders for external order ingestion.
POST /supplier-payments for financial settlement.
Repeated requests with the same key must not create duplicate business transactions.

26. Validation Rules
All required IDs must be valid UUIDs where UUIDs are used.
Quantities on sale and purchase items must be greater than zero.
Prices and monetary amounts must satisfy configured precision and non-negative constraints where applicable.
Referenced products, stores, terminals, registers, customers, and payment methods must exist and be active.
Cash-register operations require an active register session.
Refund amounts cannot exceed eligible refundable amounts.
Supplier payments cannot exceed outstanding payable amounts unless an approved overpayment workflow exists.
Promotion dates and eligibility must be valid.
Closed register sessions and finalized financial transactions must not be modified by normal update endpoints.
Server-side validation is authoritative; frontend validation is only a usability layer.
27. Date, Time & Currency
API timestamps should use ISO-8601 format.
Backend persistence should use UTC timestamps.
Store timezone should be used for business-day/reporting calculations.
Money should use decimal representations and Java BigDecimal.
Currency code should use ISO-style three-letter codes where applicable.
Currency conversion must not be assumed unless explicitly implemented.
28. Error Codes

29. API Security Requirements
All production traffic must use HTTPS.
JWT access tokens must be validated by Spring Security.
Refresh tokens must be protected and revocable.
Sensitive endpoints require explicit permissions.
Rate-limit authentication and externally exposed integration endpoints.
Never return password hashes or sensitive secrets.
Do not log access tokens, passwords, or payment secrets.
Use request correlation IDs for tracing.
Validate resource ownership/store scope before returning data.
30. Store & Data Scoping
Every store-scoped resource must be checked against the authenticated user's permitted stores. A user with access to Store A must not retrieve or modify Store B data by changing an ID in the URL.

35. Implementation Guidelines for Spring Boot
Controller
  ↓
Request DTO + @Valid
  ↓
Application Service
  ↓
@Transactional business operation
  ↓
Domain validation
  ↓
Repository
  ↓
PostgreSQL

Recommended packages:
com.pos.<module>.controller
com.pos.<module>.dto
com.pos.<module>.service
com.pos.<module>.domain
com.pos.<module>.repository
com.pos.<module>.mapper
com.pos.<module>.exception

Do not expose JPA entities directly from REST endpoints.
Use DTOs for input and output contracts.
Keep transaction boundaries in application services.
Use global exception handling with @RestControllerAdvice.
Use Spring Security method/endpoint authorization.
Use Bean Validation annotations for request validation.
Use BigDecimal for all monetary calculations.
