DATABASE DESIGN & ERD SPECIFICATION
Integrated POS, Inventory & Business Management System
PostgreSQL • Version 1.0 • Architecture Baseline


1. Purpose
This document defines the logical and physical database design for the POS Management System. It translates the approved product, requirements, and system architecture into a PostgreSQL relational model suitable for implementation with Spring Data JPA/Hibernate.
1.1 Objectives
Maintain strong transactional consistency for sales, payments, inventory, registers, and payables.
Provide traceable historical records for operational and financial activity.
Support multiple stores, terminals, and register sessions.
Support batch and expiration tracking.
Provide a scalable foundation for reporting and online orders.
Prevent invalid relationships through database constraints.

PostgreSQL is the authoritative system of record. Redis, if used, is non-authoritative and must never be the source of truth for financial or inventory balances.
3. Database Design Principles
Use UUID primary keys for major business entities to reduce predictable identifiers and support distributed integration.
Use BIGINT identity keys where high-volume append-only tables benefit from compact numeric indexes, if approved during implementation.
Use DECIMAL/NUMERIC for monetary values; never use floating-point types for financial amounts.
Use UTC timestamps at persistence level and convert to store/user timezone for display.
Use foreign keys for referential integrity.
Use unique constraints for business identifiers such as SKU, barcode, invoice number, and external order ID where appropriate.
Prefer status changes, voiding, or deactivation over destructive deletion of historical financial transactions.
Use database migrations for every schema change.
Use transaction boundaries aligned with business operations.

24. Constraints & Data Integrity
Foreign keys must prevent orphaned records.
Monetary values must be non-negative where business rules require.
Quantities must be positive for sale/purchase lines.
Inventory adjustment transactions may permit signed quantities but require a transaction type and reason.
SKU and barcode uniqueness must be enforced according to business scope.
Register sessions must prevent invalid overlapping active sessions.
Closed sales, payments, and register sessions must not be physically deleted through normal application operations.
Status transitions should be validated by application business rules and, where practical, database checks.
25. Transaction Boundaries

26. Migration Strategy
Use versioned database migrations, preferably Flyway or Liquibase.
Every schema change must be represented by a migration script.
Migrations must be applied automatically in development/test and controlled in production.
Destructive migrations require explicit review and backup/recovery planning.
Seed data should be separated from schema migrations where practical.
27. Backup & Recovery Considerations
Perform automated PostgreSQL backups.
Use point-in-time recovery where production requirements justify it.
Store backups separately from the primary database host.
Test restore procedures periodically.
Define retention, RPO, and RTO before production launch.
28. Security Considerations
Database credentials must be managed outside source control.
Application database user should have only required privileges.
Production database should not be directly accessible from the public internet.
Audit tables should have restricted modification rights.
Sensitive personal/customer information should be protected according to applicable requirements.
Payment-card data should not be stored unless specifically required and compliant with the chosen payment architecture.
29. Database Performance Considerations
Use connection pooling through the Spring Boot datasource configuration.
Keep POS transaction queries small and indexed.
Avoid loading entire product catalogs for normal POS operations.
Use pagination for large customer, supplier, inventory, and report datasets.
Monitor slow queries.
Review execution plans for high-volume queries.
Consider partitioning only after measured data volume justifies it.
